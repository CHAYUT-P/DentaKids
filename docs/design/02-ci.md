# 02 · Continuous integration

*Status: done (2026-10-23). Workflow: `.github/workflows/ci.yml`. Unit tests:
`src/lib/*.test.ts` (`pnpm test`).*

## The problem

The clinic uses this system every day, and more than one person will change
the code (an intern next). Before CI, "is it safe to deploy?" depended on
someone remembering to run four commands locally. A push to `main` deploys to
the clinic within a minute on Vercel, so a mistake reaches real families
almost immediately.

## What runs on every push and pull request

| Job | What | Why |
|---|---|---|
| **Types, lint, unit tests** | `pnpm typecheck`, desktop-app typecheck, `pnpm lint`, `pnpm test` | Seconds to run. Catches most mistakes before anything slower. |
| **Database tests** | A **fresh Postgres 16** service → `db:push --force` (schema from code) → `db:seed` → `e2e:test` (48) → `db:test` (28) → `concurrency:test` (15) | Proves the schema builds from nothing, and that the booking rules **and the concurrency guarantees** (design/01) still hold after the change. |
| **Production build** | `pnpm build` | The deploy itself won't fail on a type or route error. |

The three jobs run **in parallel**. A newer push to the same branch cancels the
older run (`concurrency: cancel-in-progress`).

## Unit tests: the money maths first

Money bugs are the most expensive kind, and the maths is pure, with no database
needed, so it's fast to test exhaustively. 16 tests in `src/lib/`:

- **billing.test.ts:** line and bill totals never go negative; a bill discount
  is shared across lines by value; doctor-fee rule priority (dentist +
  treatment → treatment → dentist → clinic default); % fee after lab cost; fixed
  fee per unit; no DF without a dentist or a rule.
- **bahtText.test.ts:** receipt amounts in Thai words, including the tricky
  ones (11 = สิบเอ็ด, 21 = ยี่สิบเอ็ด, 101 = หนึ่งร้อยเอ็ด, millions).
- **promptpay.test.ts:** the CRC matches the **published standard check value**
  (`"123456789"` → `29B1`), not just our own output. The QR fields are correct.
- **slots.test.ts / ageGroup.test.ts:** 1-hour bookings hold two slots, a
  treatment must finish inside the dentist's shift, kids/adults rules.

**Why Node's built-in test runner** (`node --test` through `tsx`) instead of
Jest or Vitest: zero new dependencies, TypeScript works through the `tsx` we
already use, and it's fast (~0.2 s).

## Decisions and trade-offs

- **Real Postgres in CI, not mocks.** The guarantees that matter (unique
  indexes, advisory locks, transactions) live *in the database*. A mocked
  database would pass while the real one fails.
- **`db:push --force`** builds the schema straight from `src/db/schema.ts` on
  the empty CI database. In production we still push by hand, **before**
  deploying code that needs new columns (see OVERVIEW §7).
- **Not yet:** the Windows installer is a separate, manually started workflow
  (it takes ~7 minutes and only matters for releases). There's no end-to-end
  browser test (Playwright) yet. The server-side e2e test covers the logic,
  not the screens.

production build ✓ (12 s), unit tests 16/16 ✓.
